Drain monitor API v1

Integration console · Download OpenAPI 3.1 contract

Base path: /api/v1. JSON bodies use Content-Type: application/json. If API_KEY is configured, every API call requires Authorization: Bearer <API_KEY>.

Sensor frame

{
  "event_id": "10000000-0000-4000-8000-000000000001",
  "device_id": "tub-01",
  "boot_id": "20000000-0000-4000-8000-000000000001",
  "sequence": 0,
  "captured_at": null,
  "source": "hardware",
  "temperature_c": 20,
  "readings": [
    {"sensor_id": "a", "status": "ok", "distance_mm": 300},
    {"sensor_id": "b", "status": "timeout"}
  ]
}

Each frame must contain sensors a and b once each. For an ok reading, send distance_mm OR echo_us. For timeout/out_of_range, omit both. US-100 UART distances are already in millimeters; do not convert them as pulse times. Omit captured_at or send null before the ESP32 clock is synchronized; timing then uses server receipt and includes network delay.

Calibration and test

POST /devices/tub-01/calibrations
{"empty_distance_mm":{"a":400,"b":420},"wet_threshold_mm":20,"dry_threshold_mm":8,"stable_samples":3,"max_gap_ms":5000}

POST /devices/tub-01/sessions
{"source":"hardware","name":"Filled-tub drainage test"}

Both sensors must first observe water above their individual wet thresholds, followed by consecutive valid readings below both dry thresholds. A failed echo is unknown, never dry. Large gaps make the result inconclusive. No claims of clog detection, corrosion detection, flow rate or validated thresholds are made.

Limits: body 16KB, history limit 1–500, session analysis at most 5000 frames, one active test per device/source. Use filled-tub tests, not shallow shower runoff, for the initial hardware validation.

Errors use {"error":{"code":"...","message":"...","request_id":"..."}}. 201 means new data, 200 means accepted retry/read, 409 means conflict, 422 means invalid payload, 503 means storage unavailable.
